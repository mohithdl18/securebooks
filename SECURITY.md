# SU VILLA Bookings — Security Notes

## What was fixed in code

| # | Issue (before) | Risk | Fix |
|---|---|---|---|
| 1 | Promo codes `SUVILLA10 / WELCOME5 / STAY15` printed on the checkout page and hard-coded in the browser bundle | Anyone gets 15% off forever | Codes now live in MongoDB (`promo_codes`) with expiry, usage caps, max discount, one-per-customer. Checked by `/api/promo/validate` (rate-limited) and re-checked in `create-order`. Manage with `scripts/promo-codes.mjs`. |
| 2 | `GET /api/Bookings?bookingId=` returned name, phone, **Aadhaar**, address to anyone with a booking ID | Personal data leak (IDOR) | Requires booking ID **and** a secret lookup token; returns no Aadhaar/address/phone, email masked. Rate-limited. |
| 3 | Full Aadhaar numbers stored in plain text | Legal exposure (Aadhaar Act, DPDP Act 2023) | Only `XXXX-XXXX-1234` is stored. Check physical ID at check-in. |
| 4 | Booking session (`TempID`) generated by the browser with `Math.random()` and trusted by the server | Anyone who learns a TempID can release or hijack another guest's holds | Server issues an unguessable HttpOnly, SameSite=Strict cookie. TempID is derived from it via HMAC; body values can't impersonate. |
| 5 | Unlimited room holds from anyone | One script can keep every room "held" 24×7 and block all bookings | Per-IP rate limit (30 holds / 10 min) + max 6 active holds per IP. |
| 6 | If the guest closed the tab right after paying, the webhook only logged it | Money taken, no booking | Webhook now runs the same `finalizePayment()` as verify, with event de-duplication. |
| 7 | Paid after the 10-min hold expired → "contact support" | Paid, no room, manual refund | If the room is still free, booking is confirmed anyway; otherwise **automatic full refund** (claimed once, safe under races). Checkout window also auto-closes before the hold lapses. |
| 8 | Double-booking protection relied only on application checks | Rare race could confirm the same room twice | New `room_nights` collection: one document per room-night with a unique `_id`. The DB itself rejects a second booking. Unique indexes on booking ID, order ID and payment ID too. |
| 9 | Payments in "authorized" state never completed | Stuck bookings if auto-capture is off | Server captures the exact expected amount. |
| 10 | `/api/test-db` public, listed DB name and collections | Reconnaissance | Dev-only, or `Authorization: Bearer $HEALTHCHECK_SECRET`. Reveals nothing. |
| 11 | `GET /api/Bookings/TempBooks` public cleanup trigger | Abuse / load | Requires `Authorization: Bearer $CRON_SECRET`. TTL index also cleans up. |
| 12 | Internal error messages returned to the browser | Information leak | Only known validation messages are shown; everything else is generic. |
| 13 | No size/format limits on customer fields; no server email/phone/PIN validation | Junk data, oversized documents | Strict server validation and length caps; 8–16 KB body limits. |
| 14 | Occupancy limits only enforced in the browser | Overbooking a room's capacity | `maxGuests` enforced on the server. |
| 15 | No security headers | Clickjacking of the payment page, XSS impact | CSP (Razorpay-only third parties), HSTS, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy. `X-Powered-By` removed. |
| 16 | "Today" computed in server timezone (UTC on Vercel) | Past-date check wrong between 00:00–05:30 IST | Uses Asia/Kolkata. Max 1 year advance booking. |
| 18 | Server charged ₹5,500–7,000/room while the site showed ₹12,999 | Guests charged a different amount than shown | One shared price list (`src/config/pricing.js`). Server never uses any price, total or discount from the browser. The browser's displayed total is only *compared*: if it differs from the server's figure, payment isn't opened. |
| 17 | Cross-site requests not blocked | CSRF defence relied on browser defaults | Origin / Sec-Fetch-Site check on every state-changing route. |

## You must do these (outside the code)

1. **Rotate keys if this zip/repo was ever shared** — Razorpay key secret, webhook secret, MongoDB password.
2. **Razorpay dashboard**
   - Webhook URL `https://<your-domain>/api/payments/webhook`, events: `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed`. Put a long random secret in `RAZORPAY_WEBHOOK_SECRET`.
   - Turn on 2FA for every dashboard user; give staff the least role they need.
   - Settings → Payment capture: automatic.
   - Whitelist your domain (Settings → Website / App details).
3. **MongoDB Atlas**
   - Must be a replica set (Atlas always is) — transactions are required.
   - App user with `readWrite` on `suvilla_bookings` only (no admin roles).
   - Network access: allow only your hosting provider's IPs, not `0.0.0.0/0` if you can avoid it.
   - Enable backups.
4. **Environment variables** — see `.env.example`. Set `APP_ORIGIN` to your live URL. Never prefix secrets with `NEXT_PUBLIC_`.
5. **Create new promo codes** (old public ones are dead):
   `node --env-file=.env.local scripts/promo-codes.mjs add WINTER12 12 --until 2026-12-31 --max-uses 50 --max-discount 3000 --once`
6. **Cron** (Vercel): add to `vercel.json`
   `{"crons":[{"path":"/api/Bookings/TempBooks","schedule":"*/15 * * * *"}]}` — Vercel sends `CRON_SECRET` automatically.
7. **Prices** live in one file: `src/config/pricing.js`. The site displays from it and the server charges from it, so they can't drift apart. Change a price there and redeploy. (GST rate: confirm with your CA.)
8. **Cancellations by staff**: when cancelling a booking manually, also delete its `room_nights` documents and remove the room from `room_availabilty.booked_rooms`, or the dates stay blocked.

## Recommended next steps

- Cloudflare Turnstile (free) on "Hold room" and "Pay" to stop bots completely.
- Send a confirmation email (Resend is already installed) containing the booking ID + lookup token link.
- An authenticated admin panel (e.g. Auth.js with Google login restricted to your staff emails) instead of editing MongoDB directly.
- Alerting on log lines `AUTO-REFUND FAILED` and `Payment/order mismatch`.
- Daily reconciliation: compare Razorpay settlements with `bookings_data`.
- Privacy policy + refund policy pages (needed for Razorpay KYC and DPDP Act compliance), and a data-retention rule (e.g. delete guest addresses 1 year after checkout).

## Admin dashboard (`/admin`)

- Login with `ADMIN_USERNAME` / `ADMIN_PASSWORD` from `.env.local` (password 10+ characters). If these or `ADMIN_CANCEL_PIN` (4–8 digits) are missing, the whole admin area stays switched off.
- Session: random token in an HttpOnly, SameSite=Strict cookie; only its hash is stored in `admin_sessions`, which MongoDB deletes after 24 hours. Logout removes it immediately. The page also signs itself out when the 24 hours are up.
- Login is limited to 5 attempts per 15 minutes per IP (30/hour overall). Wrong cancel PINs are limited to 5 per 15 minutes.
- Every admin API checks the session on the server, so the pages can't be bypassed by calling the APIs directly.
- Every login, failed login, booking view, block/unblock and cancellation is written to `admin_audit`.
- Cancelling sets the booking to `cancelled` and frees its rooms in `room_availabilty` and `room_nights`. It does **not** refund automatically.
- Blocking adds the room to `blocked_rooms` for that date in `room_availabilty`. Guests can't hold or pay for it, and a booked or currently-held room can't be blocked.
- Invoice details (name, address, phone, GSTIN) live in `src/config/business.js`.

## Offers & invoice export

- Offers are created from the admin dashboard (Offers button) and stored in `promo_codes`. Public offers are listed on the bookings page via `/api/offers`; private codes are never listed and work only if a guest types them.
- Validity counts today as day 1 and ends 23:59 IST on the last day. Discount 1–90%, applied to the booking amount before tax and platform fee — always calculated on the server.
- `/api/promo/validate` is rate-limited (8 tries / 15 min per IP), so private codes can't be guessed.
- "Download PDF" in the bookings list exports every invoice from the last N days (max 365 days / 500 invoices) as one PDF. Amounts print as "Rs." because the built-in PDF fonts have no ₹ symbol.
